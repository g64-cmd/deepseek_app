# Android 阶段 C0 测量与基线

日期：2026-11-22（Asia/Shanghai）。代码基线：`develop@981428e` 加本轮 C0 测量标识和独立 debug 包；未实施 C1 渲染优化。

**C0 工具与离线模拟器基线已完成**：75 个切换样本、10 次滚动、四个探针对照样本、独立 trace、20 轮内存往返和大备份正常恢复。混合会话热切换中位约 40.15 秒，C1 应优先隔离图表几何测量/布局成本并实施富内容按需渲染。目标真机、现代 WebView、瞬时内存峰值及存储失败路径仍待验，不将本轮结果作为阶段 C 整体验收。

## 2 夹具与指标校准

新工具位于 [scripts/perf](../scripts/perf/README.md)，旧 [perf-seed.js](../scripts/perf-seed.js) 保留供历史使用。新混合夹具包含 30 个 800 行代码块、240 个 display 公式和 30 张 30 节点 Mermaid；重图表夹具为 25 条用户消息、13 条 Mermaid 回答和 12 条公式密集回答（96 个公式）。生成器自己统计清单，并通过回归核对。

注入要求正式及 staging 表全部为空，所有写入放在同一事务；拒绝覆盖已有数据。新工具没有前缀删除或自动清库操作。实际数据只写独立 C0 包。

消息滚动层、会话项、消息和富内容状态均有稳定标识。`tailPaintProxyMs` 测程序化点击到尾部可见内容、图片和字体就绪后跨过两次 rAF；它是绘制机会代理，不是实际屏幕首帧。切换观察窗目标为 3 秒，阻塞超窗时保留实际时长，长任务不直接裁为 3 秒。屏外任务会在样本之间等待结束，其完成时间不混称可见内容就绪。

冷切换每次重启应用进程，系统与磁盘缓存不清除；热切换先预热目标场景。每场景 5 个冷样本、10 个热样本，单组未达到 20 个时不报告切换 P95。滚动 P95 指同一次滚动内的 rAF 帧间隔；不能与跨样本耗时分位数混用。完整定义见工具说明。

## 3 结果

### 切换矩阵

下表为 `tailPaintProxyMs`，单位秒。冷组每项 5 次、热组每项 10 次，所有样本可见内容检查均通过。

| 场景 | 冷中位数 | 冷最大值 | 热中位数 | 热最大值 | 热最大单个长任务 |
| --- | --- | --- | --- | --- | --- |
| 300 条纯文本 | 0.875 | 1.283 | 0.665 | 1.093 | 1.028 |
| 300 条混合 | 6.833 | 7.558 | 40.148 | 40.617 | 39.623 |
| 50 条重图表 | 6.763 | 7.332 | 6.916 | 7.460 | 7.149 |
| 五张大图 | 0.165 | 0.187 | 0.133 | 0.334 | 0.214 |
| 多层分支默认路径 | 0.100 | 0.105 | 0.097 | 0.149 | 0.080 |

采样时混合会话 DOM 中位数为冷 209,469、热 222,669，纯文本为 6,789。冷采样时仍有屏外图表未完成，两个 DOM 数值不是同一完成状态；不能把冷组更快理解为整个会话已完成。热组的约 40 秒冻结在 10 个样本中均出现，需结合独立 trace 分析 JS、布局与 GC。

原始样本位于 `tmp/c0/2026-11-22-baseline/results.json`，APK、运行时代码 patch 和当时的工具副本保留在同目录。预检 `tmp/c0/smoke/` 不并入正式统计。

[矩阵摘要与原始文件哈希](perf/c0-2026-11-22-matrix.json)已保存到仓库。热组滚动的帧间隔中位数约 16.67ms；混合场景 P95 为 33.33ms、最大 100ms。它是底部上行最多 6 秒、约 9,000 CSS px 的已渲染区域采样，不表示全部历史或所有帧都流畅。

### 首次内存采样失败

切换矩阵完成后，普通 `dumpsys meminfo PID` 采样期间渲染进程发生 native 空指针崩溃，随后 WebView 导致宿主退出。崩溃栈包含 `ActivityThread$ApplicationThread.dumpMemInfo` 和 `FastPrintWriter`；这是采样时发生的故障证据，不能据此认定自然 OOM 或应用内存泄漏。原始整次运行状态保留为 failed，75 个已完成样本仍单独可用。

工具改用本机帮助明确提供的 `dumpsys meminfo --local PID`，只由系统本地收集，不回调目标进程；已验证应用和渲染进程都可读取 PSS，完整往返补测另记。崩溃与帮助保留为 `crash-summary.log`、`meminfo-help.txt`。

另发现旧工具清单的 localStorage 标记未在强停后保留，但主库的 1,006 会话与六份原件完整；核对 ID/消息数与全部原件哈希后恢复工具元数据。新工具使用独立 IndexedDB 严格持久性事务，并已验证跨强停重启保留，不改应用主库 schema。

### Trace 与探针对照

独立 trace 已保存 48,782,618 字节，`dataLossOccurred=false`，对应[trace 摘要](perf/c0-2026-11-22-trace.json)。它带有 profiler 开销，不混入无 trace 的 75 个切换样本。

渲染主线程最长 RunTask 为 **43.024 秒**，最长 RunMicrotasks 为 **42.501 秒**；记录到的 MajorGC 单次最长 **207ms**、整个 trace 合计约 **544ms**。这些事件可能嵌套，不能相加得 CPU 百分比；本段证据不支持把约 40 秒冻结仅归于大 V8 GC。

对原生 `getBoundingClientRect` 叶帧按最近 JS 调用者归类，29,178 个采样来自与 Mermaid/Dagre 同包的 `4471.b0874c8d.js`，35 个来自 C0 探针。采样数不是 CPU 占比，也尚未定位到唯一源码函数，但为图表几何测量/布局提供了优先排查依据。

探针 v2 将就绪检查限制到末轮消息，避免逐个读取全历史富内容几何信息，并保留对附件/字体的等待。相同 APK、原始夹具下的两个混合热切换为 **37.980 / 40.074 秒**，最大单任务 **36.904 / 38.988 秒**，与 v1 矩阵范围接近；这支持冻结仍主要存在于应用路径，不能解释为仅由全历史探针造成。该四样本短对照单独保存在 `tmp/c0/2026-11-22-probe-control/`，不与 v1 组混算中位数。内存已改用 v2 独立重测。

对照的[机器可读摘要](perf/c0-2026-11-22-probe-control.json)已保存。C1 首批应优先减少屏外图表的渲染与几何查询，再分别测代码高亮、公式和 DOM 挂载成本；尚未将 minified profile 精确还原为唯一源码根因。

### 20 轮内存检查

排除一轮预热后，在同一图片会话静置 10 秒采样；四点主进程 PID 均为 11796，渲染进程 PID 均为 11827，20 轮中连接未中断。单位 MiB，数据见[内存摘要](perf/c0-2026-11-22-memory.json)。

| 往返轮次 | 应用 PSS | 渲染进程 PSS |
| --- | --- | --- |
| 0 | 99.76 | 235.60 |
| 5 | 102.24 | 806.08 |
| 10 | 103.61 | 398.67 |
| 20 | 102.54 | 807.59 |

渲染进程存在明显回落，第 20 轮高水位与第 5 轮接近，四点不足以判定泄漏或证明长期有界；约 808 MiB 的观察值仍应在 C1 与目标设备上重新评估。这里不是瞬时峰值，也没有把 JS 堆再加到 PSS。

四点的 legacy `performance.memory` 估计均约 12.11 MiB，不能据此断言堆恒定。第 20 轮结束后独立 CDP 快照在图片会话记录 `usedSize=10,378,228` 字节（约 9.90 MiB）；它不补填为原四点值。新驱动同时保存 CDP 堆用量；该 API 仍只描述对应 V8 堆，不能代替整个渲染进程内存。

## 4 规模与恢复验证

[规模驱动](../scripts/perf/run-scale.mjs)在渲染驱动结束后独立执行，通过现有设置界面测本地用量冷/热缓存、完整备份生成和原生缓存写入，再从缓存读回 ZIP，经 DOM File 输入恢复。它临时拦截 Share 请求，不启动分享接收应用；因此不宣称覆盖 SAF 和跨应用分享。

正式闭环使用重新生成的原始夹具，数据与 APK 哈希均记录于[规模摘要](perf/c0-2026-11-22-scale.json)。以下为单次测量，不作为统计分位数：

| 操作 | 结果 |
| --- | --- |
| 1,006 项侧栏展开绘制代理 | 471ms |
| 用量冷扫描 / 缓存命中至显示 | 2,643ms / 117ms；均汇总 1,336 条回复，包含未选分支 |
| ZIP 大小 / 原件合计 | 124,574,914 字节（118.80 MiB）/ 115.40 MiB |
| 生成 ZIP 至首次 native mkdir | 10,089ms，属于生成完成时间上界 |
| 原生缓存写入阶段 | 18,007ms；30 次 write/append，包含分块 base64 转换与桥接 |
| 导出至缓存总计 | 28,096ms |
| 从原生缓存读回 ZIP | 1,335ms |
| 确认导入至恢复成功显示 | 58,192ms |
| 完整性 | 1,006 会话/摘要、六份原件 SHA-256 全部一致，多层分支含未选路径的结构一致 |

2 秒间隔顺序采样的 PSS 最大观察值：导出阶段应用 **192.94 MiB**、渲染进程 **277.49 MiB**；导入阶段应用 **163.39 MiB**、渲染进程 **227.70 MiB**。各进程并非同时采样，不能把各自最大值相加称为同一时刻峰值。低存储与失败恢复不在本次正常闭环中。

原生 Filesystem 调用时间区分生成完成上界与写缓存阶段；PSS 每 2 秒采样，最大观察值不是瞬时峰值。恢复检查会话/摘要/原件数量、六份原件哈希及未选分支关系。数据准备完成不能代替这些操作的实际通过。

首次规模驱动因工具标记缺失退出；第二次恢复操作已经完成，但校验器错误地要求消息 ID 不变。现有归档会重编号，已改为比较分支结构，并加回归确认既接受重编号又拒绝分支变化；第三次从原始夹具重跑后整体通过。此前失败保留在 `2026-11-22-scale/`、`2026-11-22-scale-v2/`，不并入正式统计。

## 5 代码与工具验证

新增八项工具回归覆盖实际内容计数、确定性数据、分支结构、备份重编号、空库保护、事务失败、长任务/帧间隔统计与末轮探针。当前 **74/74**、类型检查与 lint 通过；production Web、C0 debug APK 和不带 C0 参数的常规 debug APK 构建通过。默认 APK 输出已恢复为常规包 `com.g64_cmd.whalechat`，未安装到日常应用。

实测时设备 APK 与本地 C0 APK 的 SHA-256 均为 `20652b744919d66558203b3782f2a5e5e54d784f934b73ad0a3cde15e90f7faf`。工具现会校验设备/选定 APK 一致性，并支持 `--apk=路径` 选择保存的 C0 构建；不一致时拒绝采集，防止将常规 APK 标成测试包基线。记录与构建日志保留在 `tmp/c0/`，未提交或推送。

## 6 剩余范围

- 较低性能真机、日常主力真机与现代 WebView 的性能与内存目标仍需独立固定。
- TalkBack、字体缩放、Android 15+ insets 和音频中断沿原验证记录推进，不以 C0 性能工具通过代替。
- 大备份的低存储、损坏、中断和失败恢复需要专项场景；正常恢复和 PSS 采样不能证明所有失败路径。
- 只有完成优化前后在相同条件下的对照，才能判断 C1 收益。旧阶段 B 的耗时和当前指标、内容、构建条件不同，不直接相减得性能提升。
