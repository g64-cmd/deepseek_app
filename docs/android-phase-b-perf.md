## 2. 方法

- **注入**：经 adb forward + Chrome DevTools Protocol 向 WebView `Runtime.evaluate` 执行 `scripts/perf-seed.js`（也可 chrome://inspect 手工粘贴）。合成数据直接写 IndexedDB（库 `chat-demo` v11），注入后 force-stop 重启使会话列表加载。
- **场景**：
  - 会话 A「300 条混合」：150 轮问答，assistant 内容按 1:1:1:1:1 混合 纯文本 / 200 行 TS 代码块 / 8 个 display 公式 / 30 节点 Mermaid / 思考块+文本，每条带真实量级 usage；
  - 会话 B「300 条纯文本」：同条数纯文本（对照，分离"条数"与"富内容"变量）；
  - 会话 C「重图表」：仅 50 条（25 Mermaid + 25 公式密集）；
  - 会话 D「5 张大图」：10 条消息 + 5 张 2048×1536 噪点 PNG（每张约 10.3 MB，原件入库）；
  - 侧栏另注入 1000 个 2 条消息的小会话。
- **指标**：`performance.now` 点击会话项起计时；MutationObserver 观察滚动容器至 600ms 无变更记"全量渲染完成"（`fullMs`）；PerformanceObserver `longtask`；rAF 循环匀速向上滚动 6s 统计 FPS 分布；`performance.memory` 采样；`am start -W` 与 CDP 轮询按钮就绪测冷启动。
- **已知测量噪声**：切换发生 5s 级 longtask 时，CDP evaluate 响应会排队，`firstMs` 计时会失真（夸大）；`maxLongtask` 来自浏览器 PerformanceObserver，不受影响，作为主证据。

## 5. 分析

1. **消息条数不是瓶颈**：300 条纯文本 1.5s（模拟器）/0.8s（桌面）。当前"全量 map 渲染"架构在纯文本场景到 300 条仍勉强可用。
2. **富内容同步渲染成本是瓶颈**：混合会话 DOM 节点是纯文本的 **35 倍**（232K vs 6.6K）、耗时 5~11 倍。成本构成：Prism 同步高亮（60 块×200 行）、KaTeX `renderToString`（384 个公式）、Mermaid 全局串行渲染队列（30 张，单图约 300ms——50 条重图表会话 9.3s 直接证明）。
3. **同周期重复渲染出现 49~67s 主线程冻结**（两次复现，从图片/列表会话切回已渲染过的大会话时）。首切因懒加载存在异步边界分摊了阻塞；重复渲染时全部资源就绪、同步一口气提交 245K 节点，叠加 GC/内存压力后冻结放大。根因（Mermaid 重挂载 vs GC）待阶段 C 优化后复测确认；本报告按现象记录。
4. **滚动与图片不是问题**：渲染完成后滚动 53~60 FPS 近零 longtask（DOM 已在文档流，滚动只是合成）；10.3MB 大图 blob URL 异步解码不阻塞。
5. 侧栏 1000 项全量 DOM 对切换与冷启动未见显著影响（冷启动 3s 内可交互）。

## 6. 决策（对照预定义阈值）

预定义阈值：切换全量渲染 >2s 或滚动 FPS 中位 <40 或堆峰值超基线 2 倍 → 虚拟化高优先；1~2s → 先试轻量方案；<1s → 关闭。

| 场景 | 结果 | 判定 |
| --- | --- | --- |
| 300 条混合 / 50 条重图表 | 8~17s（+49~67s 离群冻结） | **远超阈值** |
| 300 条纯文本 | 1.5s | 边缘（1~2s 档） |
| 滚动 FPS | 53~60 | 通过 |
| JS 堆 | 14MB | 通过（DOM 内存未计入，见 §3 备注） |

**决策：阶段 C 将"长会话渲染优化"列为高优先，但路线修正为"按需渲染富内容"优先于经典列表虚拟化**——重图表会话仅 50 条就 9.3s，按条数 windowing 对它无效；反之若富内容只在实际可见时渲染，300 条混合的首切成本将接近纯文本基线。建议实施顺序：

1. **消息行级 `content-visibility: auto` + `contain-intrinsic-size`**（纯 CSS，先测收益，注意与滚动跟随/锚定逻辑的相互作用）；
2. **CodeBlock/Mermaid/Math 进入视口才渲染**（IntersectionObserver 懒挂载或 React 并发拆分，Mermaid 串行队列同时评估并发度）；
3. 视 1/2 复测结果决定是否还需要**倒序虚拟化**（只渲染尾部 N 条向上加载）作为超长会话（>500 条）兜底；
4. 复测时优先追查 §5.3 的 49~67s 冻结根因。

**真机复测项**（有设备后）：WebView 140+ 全场景重测；低端设备基线。

## 7. 复现

1. 启动模拟器与 App，经 chrome://inspect 打开 WebView console，粘贴 `scripts/perf-seed.js` 后执行 `await perfSeed.inject()`、`await perfMeasure.switchTo('perf-300 条混合消息')` 等。原 CDP 临时驱动已清理，不作为复现依赖。
2. force-stop 重启后按 §2 场景依次 `switchTo` / `scrollPass`。
3. 结束执行 `await perfSeed.cleanup()` 并重启确认 `perfSeed.stats()` 归零。

合成内容模板与说明见 `scripts/perf-seed.js` 头部注释；大图会话实际生成 2048×1536 噪点 PNG（每张约 10.3MB，比方案拟定的"2MB 附件"更重，作为压力上界如实记录）。
